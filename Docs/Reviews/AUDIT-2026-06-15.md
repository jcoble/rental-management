# Rental Command — Engineering Audit Report

**Date:** 2026-06-15
**Scope:** Full-stack review of the Rental Command monorepo (`RentalCommand.*` .NET API/Engine/Data/Core, `web/` SvelteKit SSR app, `mobile/` Flutter app) at worktree `/Users/blackcolours/dev/work/worktrees/rental-management/audit-base` (release-integration-v2, merge `9417a96`).
**Specialists:** backend, data, security, web, mobile, ux.
**Method:** Per-domain specialist sweeps. Every Critical/High finding was put through an independent devil's-advocate refutation pass; only findings that **survived** refutation appear in Section 2. Medium/Low findings are reported as filed (not adversarially verified) and lightly deduped.

---

## 1. Executive Summary

The codebase is, on the whole, disciplined: portfolio scoping is applied consistently per-query, the refresh-token rotation design is thoughtful (hashed storage, single-use, family-revoke), webhook signature validators use constant-time HMAC comparison, and aggregates are mostly computed DB-side. The audit nonetheless surfaced **6 confirmed High-severity defects**, each independently verified against primary source and each survivor of a deliberate refutation attempt. They cluster into three themes:

1. **Money correctness under failure / retries.** Autopay charges Stripe with no idempotency key and records the transaction row *after* the charge returns — a crash in that window produces a real duplicate tenant debit on the next hourly cycle (no other safety net recovers it).
2. **Auth / secret integrity.** The production JWT-secret guard fails open on the exact placeholder shipped in `.env.example` (publicly-known HS256 signing key → full token forgery and cross-tenant compromise), and the Google OAuth flow ships with no `state` parameter (login-CSRF / session fixation).
3. **Tenant-facing correctness and trust.** Soft-deleted leases' payments keep inflating every financial KPI and create ghost "who's behind" rows; the mobile 401-retry path resends a consumed multipart body, intermittently failing the flagship photo/voice capture flow; and the web Reports hub shows a "we've noted your request, we'll quote it" confirmation for a request that never leaves the browser.

There were **no confirmed Critical-severity** findings and **no High/Critical findings were refuted** (the refutation pass downgraded *scope* on two of them — see the inline notes — but none were overturned).

The Medium/Low set is dominated by two recurring structural themes worth treating as programs of work rather than one-off tickets: **(a) defense-in-depth for multi-tenancy** — isolation is 100% application-layer with no Postgres RLS or EF global portfolio filter as a backstop (raised independently by 3 specialists; deduped below), and **(b) soft-delete consistency** — Payment and several other required dependents of soft-deletable principals have no matching query filter, producing 25 EF Core `10622` model-validation warnings, vestigial `DeletedAt` columns, and the root cause behind the confirmed KPI bug. A third, lighter theme is **cross-surface label/flow drift** between the web and mobile apps (the flagship "Scan/Add" vs "Capture", the "Work"/"Maintenance" cluster, raw enum labels in money forms) that undercuts the product's "one app, hand-holding" positioning.

### H-1 — Autopay off-session Stripe charges have no `IdempotencyKey`; a crash after a successful charge causes a duplicate debit next cycle

- **Severity:** High · **Confidence:** High · **Area:** Payments / Engine · **Specialist:** backend
- **Location:** `RentalCommand.Engine/Services/AutopayChargeService.cs:86-119` (charge build + `SaveChangesAsync`); guard at `:75-82`; candidate query `:45-53`. Worker cadence `RentalCommand.Engine/Workers/AutopayChargeWorker.cs:15`. Same missing key (lower-frequency, user-initiated): `RentalCommand.Api/Services/.../StripePaymentService.cs` `CreatePaymentIntentAsync` / `CreatePaymentCheckoutSessionAsync`.

**Impact.** `ChargeDueAsync` guards against double-charging only with an application-level check — `PaymentTransactions.AnyAsync(Status == Pending || Succeeded)` (`:75-82`). The Stripe charge is created via `intentService.CreateAsync(... Confirm=true, OffSession=true ...)` using `new RequestOptions { ApiKey = _config.SecretKey }` with **no `IdempotencyKey`** (verified: `grep -rn "IdempotencyKey" --include='*.cs'` returns zero hits repo-wide). The `PaymentTransaction` row that records the charge is persisted at `:119` (`await _db.SaveChangesAsync(ct)`) **after** the Stripe call returns success at `:103`. If the process is killed, the DB is briefly unavailable, or `SaveChanges` throws in the window between the successful charge and that commit, **no transaction row exists**.

Every other safety net fails to recover this window:
- The next worker cycle's candidate query (`:45-53`, `Status == Scheduled||Late`, `PaymentType==Rent`, `DueDate<=now`, active enrollment) still selects the same Payment; `alreadyInFlight` is false (no row) → it is charged a **second time** with, again, no idempotency key, so Stripe mints a brand-new `PaymentIntent` and debits the tenant again.
- The unique index on `PaymentTransaction.ProviderPaymentIntentId` (`RentalCommandDbContext.cs:1225-1227`, filtered `IsUnique`) cannot dedupe — it only dedupes once a row carrying the intent id is stored, which is precisely what failed to persist.
- The Stripe webhook (`StripePaymentService.cs:298-330`) flips `Payment.Status=Paid` only after finding the `PaymentTransaction` via `ProviderPaymentIntentId` (`:303-305`); with no row it hits the else branch, logs "No PaymentTransaction found for succeeded PaymentIntent" (`:327-328`), and leaves the (already-charged) Payment `Scheduled`/`Late` and untracked — guaranteeing re-selection.

The worker runs unattended every hour (`PollInterval => TimeSpan.FromHours(1)`), so the duplicate debit fires within ~1h. This is the distinction from the user-initiated `StripePaymentService` paths, which share the gap but don't auto-re-run.

**Concrete fix.** Pass a deterministic Stripe `IdempotencyKey` on every money-moving create call, derived from the unit of work. `Payment.PeriodKey` already exists and is documented "Used for idempotency" (`Payment.cs:20`), so for autopay use e.g.:

```csharp
new RequestOptions { ApiKey = _config.SecretKey, IdempotencyKey = $"autopay-{payment.Id}-{payment.PeriodKey}" }
```

(`payment.Id` alone is also a valid per-charge key). Stripe then returns the *original* `PaymentIntent` on a retry instead of charging again, closing the crash window regardless of when the local row is written. Apply a per-paymentId / per-session key to the interactive `StripePaymentService` paths too. Optionally also insert the `PaymentTransaction` as `Pending` (keyed on the idempotency token) **before** the Stripe call so a row always exists to dedupe on.

**Refutation result:** Attempted on five fronts (key present elsewhere; guard sufficient; unique index recovers; webhook recovers; window not reachable) — all failed. Every load-bearing claim verified against code.

### H-2 — Production JWT-secret guard misses the `.env.example` placeholder the deploy path actually uses (publicly-known signing key → full token forgery)

- **Severity:** High · **Confidence:** High · **Area:** Auth / secret handling · **Specialist:** security
- **Location:** Guard `RentalCommand.Api/Program.cs:112-121`. Placeholder `.env.example:21`. Wiring `docker-compose.yml:79` (`Jwt__SecretKey=${JWT_SECRET_KEY}`), env default `:76` (`ASPNETCORE_ENVIRONMENT=Production`). Other placeholder `RentalCommand.Api/appsettings.json:13`. Signing/validation `JwtTokenService.cs:89,124`, `Program.cs:161`.

**Impact.** `Program.cs` fails fast on a weak secret two ways: (a) length `< 32`, and (b) `!IsDevelopment() && SecretKey.Contains("CHANGE_ME_IN_PRODUCTION")`. Check (b) only matches the **appsettings.json** placeholder. The root `docker-compose.yml` (production-hardened: `no-new-privileges`, Traefik, restart policy, dataprotection volume, healthchecks; sits under the README's "## Production (docker-compose)" heading) reads `Jwt__SecretKey` from `.env`, whose template `.env.example:21` ships a **different** placeholder:

```
JWT_SECRET_KEY=CHANGE_ME_use_a_64_char_random_secret_value_here     # 48 chars
```

That value is **48 chars (passes the length check)** and does **not contain** the substring `CHANGE_ME_IN_PRODUCTION` — so **both guards pass**. A deployer who copies `.env.example → .env`, fills DB/origin, and overlooks the JWT line ships a production API whose HS256 signing key is a value committed to the public repo. With it, an attacker forges arbitrary access tokens — any `sub`, any `portfolioId`, any `Admin` role — yielding complete cross-tenant compromise and privilege escalation that bypasses every portfolio-scope check in the app. (`grep CHANGE_ME` shows exactly these three hits; no deploy script or test rejects the `.env` placeholder.)

**Concrete fix.** Make the guard reject **any** known placeholder substring and fail closed in non-Development:

```csharp
if (!IsDevelopment() &&
    jwtSettings.SecretKey.Contains("CHANGE_ME", StringComparison.OrdinalIgnoreCase))
    throw new InvalidOperationException("JWT secret is an unedited placeholder.");
```

Better: deny-list the exact strings shipped in `.env.example` and `appsettings.json`, and enforce a higher production minimum (e.g. `>= 48` chars of real entropy). Also change the `.env.example` value to one that *fails* the length/placeholder check, so a lazy copy fails closed.

**Refutation result:** Could not refute. One emphasis correction (non-fatal): the finding calls this "the documented, **primary**" path; the Hetzner runbook (`Docs/deploy-hetzner.md`) treats `deploy/docker-compose.prod.yml` (which uses `${JWT_SECRET_KEY:?...}`, fails closed) as canonical. So this is *a* documented production path, not provably *the* primary one — but the fail-open on the root `.env` route is real and exploitable, and the very existence of the line-117 guard shows the threat model is in scope; the guard is simply incomplete.

### H-3 — Google OAuth2 flow has no `state` parameter (login-CSRF / authorization-code injection / session fixation)

- **Severity:** High · **Confidence:** High · **Area:** Security / auth (SSR endpoints) · **Specialist:** web
- **Location:** `web/src/routes/auth/google/+server.ts:22-29` (consent URL built without `state`); `web/src/routes/auth/google/callback/+server.ts:15-35` (callback consumes `code` with no `state` check), cookies set `:47-82`. Server exchange `RentalCommand.Api/Services/Auth/GoogleAuthService.cs:196-236`, validations `:270-282`.

**Impact.** The authorization-code flow is implemented without the anti-CSRF `state` parameter. Initiation builds the Google consent URL with `client_id`/`redirect_uri`/`response_type`/`scope`/`access_type`/`prompt` only — no random `state` generated, no cookie set. The callback reads only `error` and `code`, then POSTs `{code, redirectUri}` to the API and **unconditionally** sets the visitor's first-party auth cookies to the exchanged identity. Server-side, `ExchangeCodeAsync` round-trips no `state` either; its only checks are `aud == ClientId` and `email_verified == true`, neither of which distinguishes an attacker-initiated flow from a victim-initiated one. (`grep` over `web/src/routes/auth/` for `state|nonce|csrf|pkce|code_verifier|code_challenge` → zero matches.)

This is textbook login-CSRF / code injection: an attacker completes consent with **their own** Google account, captures their `code`, and induces a victim's browser to top-level-GET `/auth/google/callback?code=<attacker_code>`. The callback sets new cookies, silently logging the **victim into the attacker's account** (session fixation) — the victim's subsequent documents, payment data, and notes land in the attacker-controlled account. `SameSite=lax` does **not** mitigate (a top-level GET is allowed and the callback *sets* cookies rather than relying on existing ones); `httpOnly` is irrelevant; single-use codes don't help (attacker mints a fresh one within the window); SvelteKit's built-in CSRF protection covers non-GET form posts only.

**Concrete fix.** Generate a cryptographically random `state` (`crypto.randomUUID()`) in `auth/google/+server.ts`, store it in a short-lived `httpOnly`+`SameSite=lax` cookie, and append it to the Google URL. In the callback: read `url.searchParams.get('state')`, compare against the cookie (constant-time-ish), delete the cookie, and redirect to `/login?error=google_unavailable` on mismatch/absence **before** exchanging the code. Optionally carry a signed `redirectTo` inside `state` to restore post-login navigation.

**Refutation result:** Could not refute across six angles (SameSite, single-use codes, aud/redirect_uri checks, SvelteKit CSRF, httpOnly). Practical precondition (inducing the victim to load the crafted URL) is the low bar standard to all login-CSRF; High rating holds.

### H-4 — Soft-deleted leases' payments still inflate all financial KPIs and create ghost "who's behind" rows

- **Severity:** High · **Confidence:** High · **Area:** Portfolio/soft-delete scoping; DB-side aggregates · **Specialist:** data
- **Location:** `RentalCommand.Api/Services/Domain/AccountingService.cs` — rollup `:73-92`, `GetSnapshotAsync` `:133-154`, `PastDuePaymentsQuery`/`PastDueByLeaseQuery` `:294-314`. `DashboardService.cs:105-142`. Soft-delete site `LeaseService.cs:392`. Filters `RentalCommandDbContext.cs:682` (Lease), `Payment.cs` (no `DeletedAt`, no filter).

**Impact.** `Lease.DeleteAsync` soft-deletes by setting only `DeletedAt` (`LeaseService.cs:392`) — a plain UPDATE, so the FK's cascade never fires and Payment rows persist with status unchanged (`Scheduled`/`Late`/`Partial`). Lease has a global query filter (`DbContext.cs:682`), but **Payment has none** and isn't even soft-deletable (no `DeletedAt` column). The money aggregates read `_db.Payments.Where(p => p.PortfolioId == x)` referencing only the **scalar `LeaseId` FK** (never the `Lease` navigation), so the Lease filter is never triggered. After a lease is deleted, its outstanding/late payments keep counting toward **Overdue, DueThisMonth, Collected, PastDueAmount/Count, and the "who's behind" list**.

Smoking gun: in `GetPastDueAsync`, `PastDueByLeaseQuery` (off unfiltered `Payments`) yields the soft-deleted lease's id, but the `leaseMeta` lookup (off filtered `_db.Leases`) excludes it → a **ghost "who's behind" row with null tenant/property names** plus inflated past-due counts. The delete is a normal portfolio-scoped user action (no admin gate) wired to real UI delete buttons (`web/.../leases/+page.svelte:375`, `leases/[id]/+page.svelte:257`). EF Core emits warning `10622` for exactly this required-dependent shape (see M-7).

**Concrete fix.** Make soft-delete consistent across the required-relationship graph. Cleanest: add a `DeletedAt` column to `Payment`, give it `HasQueryFilter(e => e.DeletedAt == null)`, **and** stamp `DeletedAt` on dependent Payments (and WorkOrders, etc.) in the same `SaveChanges` as the lease delete. Alternatively gate every payment aggregate on lease liveness via the navigation (`p.Lease != null && p.Lease.DeletedAt == null`), which forces EF to INNER JOIN the filtered Lease set. Add a regression test: soft-delete a lease with an overdue payment, assert it disappears from `GetPastDueAsync`/`GetSnapshotAsync`/dashboard.

**Refutation result:** Core defect confirmed and user-reachable. **Scope narrowed in place** (two overclaims corrected, finding *not* overturned):
- **Owner statements are NOT inflated.** `OwnerStatementService.cs:57-68,158-168` and `AccountingService.GetReportsAsync:808-811` reference the `p.Lease!.PropertyId` **navigation**; because `Payment.Lease` is a required relationship, EF Core 10 emits an INNER JOIN to the filtered Lease set, so those sites already exclude soft-deleted leases' payments. (The finding's own suggested grep `p.Lease != null` actually has hits there.)
- **Status `Terminated` does not trigger this** — only the explicit DELETE/soft-delete path does; "after a lease is terminated" is loose framing.

Severity remains High (prominently-displayed financial KPIs are wrong and ghost rows render), with the verifier noting it is *slightly* generous given the trigger is an explicit deletion and the splashiest claimed surface — owner statements — is unaffected.

### H-5 — 401 auto-retry resends a consumed `FormData` body — photo/voice uploads fail intermittently after a token refresh

- **Severity:** High · **Confidence:** High · **Area:** Mobile networking / auth interceptor · **Specialist:** mobile
- **Location:** `mobile/lib/core/auth/auth_interceptor.dart:125-128` (retry re-sends original `RequestOptions`), catch `:132`, reactive-only refresh (`onRequest:79-89`, no expiry check). Upload sites (single-use `FormData`): `mobile/lib/features/scan/scan_repository.dart:71` (`uploadImage`) & `:103` (`createVoiceDraft`); `maintenance/work_orders_repository.dart:112`; `inspections/inspections_repository.dart:109`; `portal/tenant_portal_repository.dart:237`; `voice/voice_intake_repository.dart:58`. Interceptor wiring `auth_repository.dart:243,261`. Server access-token TTL `JwtTokenService.cs:107`.

**Impact.** On a 401, `AuthInterceptor` refreshes the token then retries the **original** request verbatim:

```dart
final opts = err.requestOptions;
opts.headers['Authorization'] = 'Bearer $newToken';
final retryResponse = await dio.fetch<dynamic>(opts);   // re-sends the same opts.data
```

For JSON this is fine. But five repositories upload via single-use `FormData`/`MultipartFile`. Verified against the installed Dio 5.9.2 source: dispatch finalizes the **original** `FormData` in place (`dio_mixin.dart:642-646` reads `data.finalize()` with no internal clone), setting `_isFinalized == true` on the `FormData` and each `MultipartFile`. Re-finalizing on the retry throws `StateError: 'The FormData has already been finalized'` (`form_data.dart:164-171`, mirrored in `multipart_file.dart:178-188`). The strongest counter-argument — that `MultipartFile.fromBytes` uses a re-readable `_dataBuilder` — was tested and refuted: the `_isFinalized` boolean guard throws *before* `_dataBuilder` is consulted. (Dio added `clone()` precisely for this retry/redirect case.)

Exploitability is real, not theoretical: there is **no proactive/preemptive refresh** — `onRequest` attaches the stored access token with zero expiry checking, so refresh is purely reactive to a 401, which is the *designed* trigger and occurs whenever a session outlives the access-token TTL and the next action is a capture upload. Outcome on hit: `StateError` → rejected future → interceptor `catch(_)` → `handler.next(err)` surfaces the original 401 and the upload is lost with a confusing error. This lands on the app's flagship "computer does the typing for you" capture flow (receipts, work-order photos, inspection photos, voice notes) and won't show up in normal testing because it needs the token to lapse mid-upload.

**Concrete fix.** In the retry path, clone non-replayable bodies before re-sending:

```dart
if (opts.data is FormData) {
  opts.data = (opts.data as FormData).clone();
}
final retryResponse = await dio.fetch<dynamic>(opts);
```

Or have the upload repositories build their `FormData` via a factory the interceptor can re-invoke. Add a test that forces a 401-then-200 on a multipart POST.

**Refutation result:** Confirmed via primary-source reading of both app code and Dio 5.9.2 source; six refutation angles failed. One cosmetic inaccuracy in the finding: the path prefix `scan/data/` is wrong — the actual file is `features/scan/scan_repository.dart` — but the file set and line numbers are otherwise accurate. Bug is genuine and impactful.

### H-6 — Reports hub "custom report request" is a dead-end that silently drops the request while showing a success message

- **Severity:** High · **Confidence:** High · **Area:** Web — Reports / broken flow · **Specialist:** ux
- **Location:** `web/src/routes/(protected)/reports/+page.svelte:97-116` (`submitCustomRequest`), copy `:205-207`. Read-only API surface `RentalCommand.Api/Controllers/ReportsController.cs` (13 `[HttpGet]`, zero `[HttpPost]`), client `web/src/lib/api/endpoints/reports.ts`.

**Impact.** The "Need a report you don't see?" form writes the text **only to `localStorage`** under `rc.reports.customRequests`, carrying the author's own `// TODO: POST { text } to a future /reports/requests endpoint; for now persist locally.`, then shows the toast: *"Thanks — we've noted your request. Custom reports are a paid add-on, so we'll quote it before building anything."* The card body repeats the promise. The `catch` block swallows storage failures and shows the **same success toast** even when nothing was stored. To the landlord this reads as a real intake that reaches the company and triggers a follow-up quote; in fact nothing is sent server-side, no other code reads the key back, and the "future endpoint" genuinely does not exist (`ReportsController` is read-only; the endpoints client header states "every report is a pure GET"). The request dies in browser storage and is lost on cache clear / another device. Mobile has no equivalent surface, so this is web-only.

**Concrete fix.** Either (a) POST to a real endpoint (even a lightweight `/reports/requests` or an operator email/notification) so the promise is honored, or (b) until that exists, make the affordance honest — drop the success-with-promise copy and open a `mailto:`/contact link, or hide the form. Do **not** show a "we've noted your request" confirmation for data that never leaves the browser.

**Refutation result:** Could not refute. `grep` across `*.ts/*.cs/*.svelte/*.dart` for the request key / route returns hits only inside this one file; the read-only controller confirms the endpoint's absence; no mobile equivalent. The only soft point is the relative claim "the clearest dead-end found" (a judgment call, not a factual error). Verifier notes a defensible Medium argument exists (non-destructive secondary affordance) but the false customer-facing promise justifies High either way.

### M-1 — No Postgres row-level security; tenant isolation rests entirely on per-query `PortfolioId` filters *(merged: backend + security + data)*
- **Area:** Authorization / multi-tenancy (defense-in-depth) · **Files:** `RentalCommand.Data/RentalCommandDbContext.cs` (all 12 `HasQueryFilter` calls are `DeletedAt == null` soft-delete only — lines 150,166,391,573,608,637,654,682,760,803,878,936); `Program.cs:127-129` (only `AuditSaveChangesInterceptor`); base scope from JWT claim in `Controllers/AuthenticatedPortfolioControllerBase.cs:26-34`.
- **Detail:** Scope is taken from the JWT `portfolioId` claim and enforced purely by ~372 hand-written `.Where(x => x.PortfolioId == portfolioId)` occurrences. There is **no** Postgres RLS (`grep -rni 'row level security|CREATE POLICY|current_setting'` → 0) and **no** global EF portfolio filter. Discipline is currently good (`PortfolioScopeGuards.cs` centralizes FK cross-tenant checks; the base controller throws on a missing claim; sampled services — Banking, Portal, NotificationService, ExpenseService, PropertyService, TenantService, ConversationService, DocumentsController — all filter correctly, so **no concrete IDOR was found**). But a single future query/report/admin endpoint/join that forgets the predicate silently leaks or mutates another portfolio's financial + PII data, with nothing at the DB layer to catch it. (Notably, the sibling EdiPlatform project *does* use RLS on ~39 tables.)
- **Fix:** Add a second enforcement layer that fails closed: (a) Postgres RLS keyed on a per-request `SET app.current_portfolio` GUC applied via an Npgsql connection interceptor (set from the JWT claim), and/or (b) an EF global query filter on `IPortfolioScoped` driven by an injected `ICurrentPortfolio`. Prefer RLS for **write** protection (global filters cover reads only). Pair with a meta-test asserting every portfolio-scoped `DbSet` is reachable only through a scoped path.

### M-2 — SecurityDeposit return status mislabeled as "PartiallyReturned" when deductions ≥ deposit (net $0)
- **Area:** Domain / Money · **File:** `RentalCommand.Api/Services/Domain/SecurityDepositService.cs:173-179` · **Specialist:** backend
- **Detail:** `ReturnAsync` computes `net = Math.Max(0m, Amount - totalDeductions)` then `Status = totalDeductions > 0m ? PartiallyReturned : Returned`. The inline comment says "Returned only when net == original amount," but the decision is based solely on whether *any* deduction exists. When `totalDeductions >= Amount`, the tenant gets back $0 yet it's recorded as **PartiallyReturned** — feeding the move-out statement PDF and the audit row (`:186-196`). A fully-withheld deposit reads as "partially returned $0.00" on tenant-facing / dispute docs.
- **Fix:** Decide status from the outcome: `Status = net <= 0m ? Withheld : net >= Amount ? Returned : PartiallyReturned`. At minimum add a `net == 0` branch and align the comment with the code.

### M-3 — Refresh-token single-use rotation is not transactional/concurrency-guarded across processes
- **Area:** Auth / Concurrency · **File:** `RentalCommand.Api/Services/Auth/JwtTokenService.cs:194-282` · **Specialist:** backend
- **Detail:** `RefreshTokenCoreAsync` reads the token, checks `IsUsed||IsRevoked`, sets `IsUsed=true`, `SaveChangesAsync` — with no DB transaction/locking and no concurrency token (no `UseXminAsConcurrencyToken`/`IsRowVersion` on `RefreshToken`). The in-flight de-dup (`InFlightRefreshes`, `:56`) is a per-process static; the code's own comment notes the mobile Dio interceptor is a separate process from the web SSR node. Two concurrent refreshes of the same token on different instances can both see `IsUsed=false`, both rotate, and both mint pairs (lost update undetected) — weakening single-use/theft-detection semantics so a replay can succeed instead of tripping family-revoke. The 30s `RecentlyRotated` grace is also per-process.
- **Fix:** Make rotation atomic/conditional at the DB level — either add a concurrency token and treat `DbUpdateConcurrencyException` as "already rotated," or claim via a conditional `UPDATE ... WHERE Id=@id AND IsUsed=false` (`ExecuteUpdateAsync`, act only when 1 row affected). Keep the in-flight map as a fast-path optimization, not the correctness boundary.

### M-4 — Tenant "Pay now" / Stripe Checkout launch ignores `launchUrl` failure — silent dead-end with no browser
- **Area:** Platform integration (`url_launcher`) / UX · **File:** `mobile/lib/features/home/home_shell.dart:452-456` (`_open`), callers `:460-514` · **Specialist:** mobile
- **Detail:** `_open` does `final uri = Uri.tryParse(url); if (uri == null) return; await launchUrl(uri, mode: LaunchMode.externalApplication);` — the boolean result is discarded and there's no try/catch. `_payNow`/`_enrollAutopay` set a spinner, call `_open`, clear the spinner in `finally`.
