Rental Command · Foundation replacement

Blueprint compliance review

Review date: 2026-07-16. This compares the approved 2026-07-10 foundation blueprint with the current tsk-668-670-672-674-foundation-rewrite worktree, the stabilization handoff, and the retained 2026-07-15 E2E evidence. It is a source-and-evidence audit; no new browser/device run was performed because the requested sequence is review, fix, then run the E2E skill.

28confirmed blueprint discrepancies
2critical model/truth defects
14high product or correctness defects
6major acceptance gates still unproven

Verdict

The foundation is substantial, but it is not blueprint-complete and is not ready for acceptance. The canonical tenancy/account kernel, scoped team assignments, separate notification domains, atomic command infrastructure, and six Unit labels are real. The most consequential misses are not cosmetic: demo lifecycle truth contradicts itself, the approved expense model was not built, Unit Money is a receipt list rather than the promised command center, reporting drops legitimate expenses and performs forbidden in-memory composition, SingleRental still uses the redundant drill-down the blueprint removed, typed mobile intents and workspace BYOK are absent, and the destructive cutover retained compatibility models/routes.

Source of authority: the approved blueprint is the contract. The handoff and prior E2E results are evidence, not substitutes for the contract.

What should be preserved

Domain/kernel work

Canonical LeaseManagement/TenantAccount/Agreement entities and DB projections; append-only ledger; deposit commands; immutable legal artifacts; receipt-backed atomic commands; atomic audit/outbox/inbox and worker claims.

Roles and notifications

Four team presets, multiple independently scoped assignments, same-assignment capability/scope checks, relationship experiences, separate alert/routing/notice domains, versioned workspace templates, and legal review gates.

Client foundations

Six Unit labels, hidden outer Rentals row while Unit detail is active, global/contextual Scan/Add entry points, typed capture context, server-backed global list state, and purpose-built Leasing/Maintenance/Owner shells.

Already proven fixes

Visible invalid-login behavior, Guided Setup resume detection, contextual Unit scan naming, public application intake under token-scoped RLS, team-recipient SQL translation, and deterministic Messages back navigation.

Verification gaps, not yet classified as source defects

  1. Google OAuth callback registration and a real success path.
  2. Positive Property Manager, Leasing Agent, Maintenance Technician, Owner, and Tenant identities with scope/capability walkthroughs.
  3. Physical-device mobile proof, dynamic text, screen reader, modal Back order, predictive Back, and process restoration.
  4. Executed-agreement fixtures covering issue/sign/possession, correction, renewal, month-to-month, successor, ending, and history.
  5. Generated SQL and PostgreSQL plans for Units, Accounting Reports, Security Deposits, report aggregation, authorization, and selectors against the current SHA.
  6. Exact current clean SHA deployed without resetting preserved preview data, then re-walked before merge/Notion closeout.

Confirmed discrepancies

The list below is intentionally last and is the proposed fix backlog. “Confirmed” means directly supported by current source or by the handoff’s retained live preview evidence. Items based only on missing runtime proof are kept in the preceding section.

D01 · Critical · Canonical lifecycle truth

Unit, agreement, account, household, and money facts contradict one another in the current deterministic sample data.

The canonical demo seeder gives Units 18 and 19 possession and lifecycle facts without issuing or executing the draft Agreement required by the current-agreement projection. It also combines a planned move-out with an undecided tenancy and maps Unit 19 to a current unpaid account. The resulting UI deterministically recreates “occupied/current tenant but no governing Agreement” and “overdue money but no active account” contradictions, breaking the blueprint’s single possession/lifecycle/account truth.

  • CanonicalDemoLeaseSeeder.cs lines 60 and 227 onward
  • LeaseLifecycleProjections.cs lines 257, 288, and 414
  • Handoff lines 35–46 and retained Rental E2E evidence
D02 · Critical · Financial model

The approved exclusive expense scope and typed balanced allocations were never implemented.

Expense independently permits nullable Property, Unit, and WorkOrder IDs and has no operational-scope discriminator or Property/Unit/OwnerEntity allocation rows. A service comment explicitly acknowledges that typed allocations do not exist.

  • Blueprint lines 248 and 261–267
  • Expense.cs lines 6–63
  • ScheduleEService.cs lines 119–124

D06 · High · Hard SQL rule

Cash-flow composition is performed in memory after materialization.

Income and expense groups are materialized into dictionaries and then joined to an in-memory month sequence to calculate net values. The blueprint and repository rule require grouping, joining, sorting, and aggregate shaping in one translated SQL statement or database view.
