# Conversational voice intake — speak it, the app fills the fields and asks for the rest

Spoken-command intake for the non-technical landlord. He talks in plain words;
the app extracts what it can, **asks (out loud + on screen) for any missing
required field**, then shows a one-tap "Save it?" card. This is the "computer
does the typing for you" premise applied to speech — the same scan→draft→confirm
pipeline, pointed at a microphone instead of a photo.

Distinct from, and a layer above, the App Actions deep links (TSK-26): those can
only *navigate* ("scan a document" → opens a tab). This is where the command
actually *happens*.

## Problem

- A non-technical user won't reliably speak a perfectly-formed sentence with
  every field. If he says *"log a plumbing expense for 123 Main"* and omits the
  amount, today's flow either fails validation or drops him into a form to type
  the missing piece — defeating the whole point.
- The existing in-app voice note (buried in scan capture) is single-shot: record
  → draft → review form. No back-and-forth, no "you forgot the amount."
- App Actions / "Hey Google" can't fill this gap: deep links pass a few words and
  navigate; they can't run the extraction or hold a conversation.

## Goal

A first-class **"Tell me"** voice flow:

1. Tap a prominent mic → speak.
2. App transcribes + extracts intent and fields (reusing the server voice stack).
3. For each missing **required** slot, the app **speaks and shows a short
   question** ("How much was it?"); he taps to answer. Repeat until complete.
4. Ambiguous entities are asked, not guessed ("Which one — Main St or Main Ave?").
5. A plain-language **"Save it? [Yes] [Fix]"** card; **Yes** creates the record
   via the existing confirm path. Record-creating actions always end on a confirm
   tap (decided).

**v1 scope: Expenses only** — the most-built path — to prove the conversation
loop end-to-end. Payments and work orders are a fast-follow (the server already
classifies all three).

## Non-goals (v1)

- Fully hands-free auto-listen (no tap between turns) — v2; needs endpointing/VAD.
- Payments, work orders, reminders/texts, spoken-back Q&A — fast-follow.
- Live "Hey Google" App Actions recognition — needs Play Store publish + Google
  review; the TSK-26 deep-link doorway can later launch straight into this flow.
- Custom TTS voices — use the platform's built-in.

## What already exists (reused, not rebuilt)

- `POST /api/v1/voice/drafts` (`VoiceController` → `VoiceIntakeService`): audio →
  **Whisper** transcript → LLM classification into `Expense|Payment|WorkOrder`
  with per-field `{value, confidence}`, **grounded** against the portfolio's
  properties/units/tenants (so spoken "123 Main" already resolves to a
  `property_id`). Persists a `ScanDraft` (`Status = "Reviewing"`).
- `POST /api/v1/scans/{id}/confirm` → creates the Expense/Payment/WorkOrder.
- Mobile: `AudioRecorder` (`record` pkg) + `createVoiceDraft` already capture and
  upload a voice note in `scan_capture.dart`.

The conversation is the missing middle: *what's still needed* and *asking for it*.

## Design

### 1. Server — required-slot awareness + next question (`VoiceIntakeService`)
Extend the classification result (and `ScanDraftResponse`, or a thin voice DTO
wrapping it) with:
- `recordType` — already have `TargetEntityType`.
- `missingRequired: string[]` — required slots still empty for `recordType`,
  computed by **rules** (server owns the rules; client stays dumb).
- `ambiguous: [{ field, options: [{id,label}] }]` — e.g. a spoken property that
  matched >1 grounded record, or a parsed field below a confidence threshold.
- `nextPrompt: string?` — one short, natural question for the first
  missing/ambiguous slot ("How much was the plumbing bill for 123 Main?"),
  generated by the LLM with a template fallback; `null` when nothing is needed.
- `complete: bool` — `missingRequired` and `ambiguous` both empty.

**Required-slot rules — v1 Expense:** `amount` (required), `property_id`
(required, but "no specific property / general" is an accepted answer). `category`,
`vendor_name`, `transaction_date` optional (date defaults to today). Rules live in
a small `RecordSlots` map so adding Payment/WorkOrder later is a data change.

Backwards-compatible: when `missingRequired`/`ambiguous` are empty the response is
equivalent to today's draft, so the existing scan/review screen still works.

### 2. Server — fill one slot from a follow-up answer
`POST /api/v1/voice/drafts/{id}/answer` — `multipart/form-data` (`audio` or
`transcript`). Transcribes the answer, then asks the LLM to **merge** the answer
into the draft's existing `ExtractedFields` *in the context of the pending slot*
(grounding reused), updates the persisted draft, recomputes
`missingRequired`/`ambiguous`/`nextPrompt`, and returns the same shape. The client
loops on this until `complete == true`.
Stateful (draft-id) chosen over a stateless "send the whole running context each
turn" because the draft is already persisted and the confirm path keys off its id.

### 3. Client — the "Tell me" screen (`mobile/lib/features/voice/`)
A small, well-bounded feature module:
- **Entry:** a prominent mic on the Home tab ("Tell me"); later also reachable
  from the TSK-26 App Actions doorway.
- **State machine:** `idle → listening → thinking → (asking ↔ listening) →
  review → saving → done`, driven by the server's `nextPrompt`/`complete`.
- **Capture:** reuse `AudioRecorder` (`record`); gate the mic while TTS speaks so
  it doesn't record its own prompt.
- **Speak-back (decided):** `flutter_tts` reads each `nextPrompt`; the text is
  also shown. He taps the mic to answer → `/voice/drafts/{id}/answer`.
- **Running summary:** a plain-language line of what's captured so far
  ("Plumbing expense · 123 Main · amount: —"), so it's obvious what it heard.
- **Confirm:** on `complete`, show the **"Save it? [Yes] [Fix]"** card →
  **Yes** = existing `confirm` → toast + done; **Fix** = open the existing
  review/edit screen pre-filled.
- **Repository:** `VoiceConversationRepository` wraps the two endpoints; a
  Riverpod controller holds the turn state. No business logic in widgets.

### 4. Disambiguation & safety
- Ambiguous entity or a sub-threshold field → surfaced as `ambiguous`; the client
  shows the spoken question **and** tappable choices (faster than re-speaking a
  name). "No specific property" is always an option for expenses.
- Every record-creating action ends on the explicit confirm tap (decided).
- Mishearing is caught by the summary + confirm card before anything is saved.

### 5. New dependency
- `flutter_tts` (Flutter) for speaking prompts. Small, maintained, Android+iOS.

## Data flow
```
mic → audio → POST /voice/drafts
        → { recordType, fields, missingRequired, ambiguous, nextPrompt, complete }
  while !complete:
     speak(nextPrompt) + show it → tap → mic → audio
        → POST /voice/drafts/{id}/answer → { …updated… }
  → "Save it?" summary card → POST /scans/{id}/confirm → Expense created
```

## Testing (focused — per project posture)
- **.NET:** unit tests for the slot-rules + missing/next-prompt computation given
  partial Expense extractions (amount missing → asks amount; property ambiguous →
  asks property; complete → no prompt). A test that `/answer` merges a numeric
  amount into an amount-less draft.
- **Flutter:** unit test for the turn-state reducer (server response → next UI
  state); one widget test driving idle→asking→review on canned responses.
- **Manual:** the missing-amount walkthrough on the emulator/S22.

## Risks / notes
- STT on amounts/property names — grounding + disambiguation + the confirm card
  mitigate; Whisper handles "forty bucks" → 40.
- Extra round-trip per missing field — acceptable; only required slots are asked.
- TTS/record interplay — never record while speaking; disable the mic until TTS
  `completionHandler` fires.
- Touching the shared voice pipeline — keep single-shot behavior intact
  (empty `missingRequired` ⇒ same as today) so scan capture is unaffected.

## Deferred (fast-follow tasks)
- Payment + WorkOrder slot rules (server already classifies them) and their
  confirm paths.
- "Just do it" tier: reminders + tenant texts (reuse messaging/SMS) with Undo.
- Spoken-back natural-language Q&A via `POST /ai/ask`.
- Fully hands-free auto-listen (endpointing).
- TSK-26 App Actions doorway → launch directly into "Tell me" listening (needs
  Play Store + Google review for live Assistant).
